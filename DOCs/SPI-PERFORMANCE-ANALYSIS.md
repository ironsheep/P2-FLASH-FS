## 1. Current SPI Implementation

The SPI layer in `flash_fs.spin2` (lines 2787–2887) uses a **hybrid smart-pin + bit-bang** approach implemented in inline PASM2.

### Pin Assignments (Fixed in Hardware)

```
SF_CS    = 61   ' Chip select (active low)
SF_SCLK  = 60   ' SPI clock
SF_MOSI  = 59   ' Master out / slave in (DI / IO0)
SF_MISO  = 58   ' Master in / slave out (DO / IO1)
```

### Clock Generation

The SPI clock is generated by a **smart pin** in transition output mode (inverted for SPI Mode 3):

```
wrpin  ##%001000000_01_00101_0, #SF_SCLK   ' transition output, inverted
wxpin  #4, #SF_SCLK                         ' 4 sysclk per transition
```

This gives **8 system clocks per SPI bit** (4 clocks per half-cycle × 2 half-cycles).

### Data Transfer

**MOSI (send)**: The COG bit-bangs data out MSB-first using `shl`/`drvc` in a tight `rep` loop (8 sysclk per bit). Hub data is streamed in via `rdfast`/`rfbyte` (the P2 hub FIFO, not the streamer).

**MISO (receive)**: The COG samples data with `testp`/`rcl` in a `rep` loop (8 sysclk per bit), writing bytes to hub via `wrfast`/`wfbyte`.

Each byte requires the COG to **reset and restart the smart pin clock** (`fltl`/`drvl`/`wypin #16`), generating exactly 16 transitions (8 SPI clocks) per byte. A `rep @.r, #1` block around this protects the clock start sequence from interrupts.

### Flash Commands Used

| Operation | Command | Opcode | Notes |
|---|---|---|---|
| Read data | Read Data | `$03` | Standard SPI, max 50 MHz clock |
| Page program | Page Program | `$02` | Standard SPI, 256 bytes/page |
| Write enable | Write Enable | `$06` | Required before every program/erase |
| Sector erase | Sector Erase (4KB) | `$20` | ~45 ms typical |
| Read status | Read Status Register-1 | `$05` | Polled for BUSY bit |
| Read UID | Read Unique ID | `$4B` | 64-bit unique chip ID |

## 2. Current Throughput

### SPI Clock Rate

| System Clock | SPI Clock | Calculation |
|---|---|---|
| 200 MHz | 25.0 MHz | 200 / 8 |
| 300 MHz | 37.5 MHz | 300 / 8 |
| 320 MHz | 40.0 MHz | 320 / 8 (common in test/demo code) |
| 350 MHz | 43.75 MHz | 350 / 8 |

All of these are under the 50 MHz limit of the Read Data (`$03`) command, so the current implementation works correctly.

### Read Throughput (4 KB Block)

At 320 MHz system clock (40 MHz SPI):

```
Command overhead:  4 bytes × 8 bits / 40 MHz       =     0.8 µs
Data transfer:     4096 bytes × 8 bits / 40 MHz     =   819.2 µs
                                                      ---------
Total per block read:                                   820.0 µs

Throughput:  4096 / 820.0 µs  =  5.0 MB/s
```

Per-byte overhead from the `fltl`/`drvl`/`wypin` clock restart sequence (6 instructions = ~12 sysclk) adds approximately 50% to the theoretical minimum, but this is already folded into the 8-sysclk-per-bit rate since the `rep` loop and clock restart are pipelined.

### Write Throughput (4 KB Block)

Writing a 4 KB block involves erase + 16 page programs:

```
Sector erase:                                          45,000 µs  (typical)
Per page (×16):
  Write Enable command:     1 byte                         0.2 µs
  Page Program command:     4 bytes                        0.8 µs
  Data transfer:            256 bytes × 8 / 40 MHz        51.2 µs
  Internal program time:                                 400.0 µs  (typical)
  Status polling overhead:                                ~5.0 µs
                                                        -------
  Per page total:                                        457.2 µs
16 pages:                                              7,315.2 µs

Total per block write:  45,000 + 7,315  =             52,315 µs  (~52.3 ms)

Throughput:  4096 / 52,315 µs  =  78.3 KB/s
```

The erase time (45 ms) is **86% of the total write time**. The SPI bus transfer is only ~1.6% of total write time.

### Mount Time (Scanning All Blocks)

`mount()` reads the first byte of all 3,968 blocks to build translation tables:

```
Per block:  ~1.0 µs (command + 1 byte read)
Total:      3,968 × ~1.0 µs  ≈  4.0 ms
```

Plus block state analysis overhead in Spin2. Total mount time is dominated by the Spin2 processing, not SPI.

## 3. Flash Chip Capabilities

The W25Q128JV supports three SPI interface modes:

### Read Performance

| Command | Opcode | Mode | Max Clock | Bits/Clk | Peak Throughput |
|---|---|---|---|---|---|
| Read Data | `$03` | Standard (1-1-1) | **50 MHz** | 1 | 6.25 MB/s |
| Fast Read | `$0B` | Standard (1-1-1) | 133 MHz | 1 | 16.6 MB/s |
| Fast Read Dual Output | `$3B` | Dual out (1-1-2) | 133 MHz | 2 | 33.3 MB/s |
| Fast Read Dual I/O | `$BB` | Dual I/O (1-2-2) | 133 MHz | 2 | 33.3 MB/s |
| Fast Read Quad Output | `$6B` | Quad out (1-1-4) | 133 MHz | 4 | 66.5 MB/s |
| Fast Read Quad I/O | `$EB` | Quad I/O (1-4-4) | 133 MHz | 4 | 66.5 MB/s |

The current driver uses **Read Data (`$03`)**, which limits the clock to **50 MHz**. Switching to **Fast Read (`$0B`)** would unlock clock rates up to **133 MHz** — the only cost is 8 extra dummy clocks per transaction.

### Write Performance

| Command | Opcode | Mode | Page Size | Internal Time (typ) |
|---|---|---|---|---|
| Page Program | `$02` | Standard (1-1-1) | 256 B | 0.4 ms |
| Quad Page Program | `$32` | Quad input (1-1-4) | 256 B | 0.4 ms |

Write throughput is **dominated by internal flash timing**, not SPI bus speed:

- At 133 MHz standard SPI: 256 bytes transfer = 15.4 µs, but internal program = 400 µs
- The SPI transfer is only 3.7% of the page program cycle
- Even at infinite SPI speed, write throughput would improve from ~78 KB/s to only ~87 KB/s

### Erase Timing

| Command | Size | Typical | Maximum |
|---|---|---|---|
| Sector Erase (`$20`) | 4 KB | 45 ms | 400 ms |
| Block Erase (`$52`) | 32 KB | 120 ms | 1,600 ms |
| Block Erase (`$D8`) | 64 KB | 150 ms | 2,000 ms |
| Chip Erase (`$C7`) | 16 MB | 40 s | 200 s |

## 4. P2 Edge Hardware Constraints

The P2 Edge Module connects **only 4 pins** to the SPI flash chip:

| Pin | Flash Signal | SPI Role |
|---|---|---|
| P58 | DO (IO1) | MISO — data out from flash |
| P59 | DI (IO0) | MOSI — data in to flash |
| P60 | CLK | SPI clock |
| P61 | /CS | Chip select |

**IO2 (/WP) and IO3 (/HOLD)** on the W25Q128JV are **not connected** to P2 GPIO pins. They are typically tied high on the module.

### Consequence

- **Quad SPI is not possible** — requires IO2 and IO3
- **Dual SPI is possible** — uses IO0 (P59) and IO1 (P58) bidirectionally. Both pins are available and adjacent to the clock, with smart pin routing reachable (P59 = SF\_SCLK - 1, P58 = SF\_SCLK - 2)
- **Standard SPI** is the current and simplest mode

## 5. P2 Streamer Overview

The P2 streamer is a hardware DMA engine built into each COG. Once started, it moves data between hub memory and pins **at the system clock rate** with **zero COG involvement** — the COG can do other work or wait with `WAITXFI`.

### How It Works

1. **Set up the hub FIFO**: `RDFAST` (hub → streamer → pins) or `WRFAST` (pins → streamer → hub)
2. **Set the data rate**: `SETXFRQ` programs an NCO to control bit timing
3. **Start the transfer**: `XINIT mode, count` begins streaming
4. **Wait for completion**: `WAITXFI` blocks until all data is transferred

The mode word encodes: direction, pin number, bit width (1/2/4/8/16/32), byte order, and transfer count.

### Key Modes for SPI

| Mode Constant | Value | Purpose |
|---|---|---|
| `X_RFBYTE_1P_1DAC1` | `$8000_0000` | Stream bytes from hub FIFO → 1 pin (SPI MOSI) |
| `X_1P_1DAC1_WFBYTE` | `$C000_0000` | Capture 1 pin → bytes to hub FIFO (SPI MISO) |
| `X_PINS_ON` | `$0080_0000` | Enable pin output |
| `X_ALT_ON` | `$0001_0000` | MSB-first bit order |

### Streamer vs. Current Bit-Bang

| Aspect | Current (Bit-Bang) | Streamer |
|---|---|---|
| COG busy during transfer? | Yes — `rep` loop for every bit | No — set-and-forget |
| Max data rate | sysclk/8 (loop timing) | sysclk/2 (hardware) |
| Hub memory access | `rfbyte`/`wfbyte` (manual) | Automatic via FIFO |
| Setup complexity | Simple inline PASM | Mode word configuration |
| Per-byte overhead | Clock restart sequence | None (continuous) |

The critical difference: the current implementation's **8 sysclk per bit** is limited by the software loop speed. The streamer can output/capture bits at up to **2 sysclk per bit** — a 4x clock rate improvement.

## 6. Could the Streamer Help?

### Reads: Yes — Significant Improvement Possible

The streamer would help reads in two ways:

1. **Higher SPI clock rate**: Remove the 8-sysclk-per-bit software loop bottleneck. With the streamer, the SPI clock can go as fast as the flash chip allows.

2. **Free the COG**: During a 4 KB block read, the COG currently spends ~820 µs in the `rep` loop. With the streamer, the COG issues `XINIT` + `WAITXFI` and is free to do other work (e.g., CRC computation on previously read data, or servicing other tasks).

**However**, a prerequisite is switching from **Read Data (`$03`)** to **Fast Read (`$0B`)**. The `$03` command limits the clock to 50 MHz — even with the streamer, you'd only gain from ~40 MHz to 50 MHz (a modest 25% improvement). Fast Read unlocks the full 133 MHz chip limit.

#### Projected Read Throughput

| Configuration | SPI Clock | 4 KB Read Time | Throughput | vs. Current |
|---|---|---|---|---|
| **Current** (bit-bang, `$03`) | 40 MHz | 820 µs | 5.0 MB/s | baseline |
| Bit-bang, `$0B`, sysclk/8 | 40 MHz | 820 µs + 1.6 µs dummy | 5.0 MB/s | ~1x |
| **Streamer, `$0B`, sysclk/4** | 80 MHz | 410 µs | **10.0 MB/s** | **2.0x** |
| Streamer, `$0B`, sysclk/3 | 106 MHz | 310 µs | 13.2 MB/s | 2.6x |
| Streamer, `$0B`, sysclk/2.5 | 128 MHz | 256 µs | 16.0 MB/s | 3.2x |

Note: at 320 MHz sysclk, sysclk/2 = 160 MHz which exceeds the chip's 133 MHz max. The practical ceiling is around **128 MHz** (sysclk/2.5), yielding ~3.2x faster reads.

#### Dual SPI (If Implemented)

| Configuration | SPI Clock | 4 KB Read Time | Throughput | vs. Current |
|---|---|---|---|---|
| Streamer, Dual `$3B`, 80 MHz | 80 MHz | 205 µs | 20.0 MB/s | 4.0x |
| Streamer, Dual `$BB`, 106 MHz | 106 MHz | 155 µs | 26.4 MB/s | 5.3x |

Dual SPI doubles the data rate per clock by using both IO0 and IO1 for data. The streamer supports 2-pin modes natively.

### Writes: No — Flash Internal Timing Dominates

For writes, the bottleneck is the flash chip's internal timing, not the SPI bus:

```
Current write (4 KB block):
  Erase:              45,000 µs  (86.0% — chip internal)
  16× page program:    6,400 µs  (12.2% — chip internal)
  16× SPI transfer:      819 µs  ( 1.6% — SPI bus)
  Overhead:              96 µs  ( 0.2% — commands, status polls)
                      --------
  Total:              52,315 µs

With streamer (instant SPI):
  Erase:              45,000 µs  (87.4%)
  16× page program:    6,400 µs  (12.4%)
  16× SPI transfer:       ~0 µs  ( 0.0%)
  Overhead:              96 µs  ( 0.2%)
                      --------
  Total:              51,496 µs
```

Eliminating SPI transfer time entirely saves only **819 µs out of 52,315 µs** — a 1.6% improvement. Write throughput would go from 78.3 KB/s to 79.5 KB/s.

**Writes are fundamentally flash-limited, not SPI-limited.** The streamer would not meaningfully improve write performance.

### Mount: Minimal Impact

Mount scans 3,968 blocks reading 1 byte each. At ~1 µs per block, total SPI time is ~4 ms. Even halving this to 2 ms would be negligible compared to the Spin2 processing time for building translation tables. The streamer is not beneficial for mount.

## 7. Improvement Options

Ranked by impact and implementation effort:

### Option 1: Switch to Fast Read (`$0B`) — Easy, Unlocks Future Gains

**Change**: Replace the Read Data command (`$03`) with Fast Read (`$0B`) in `flash_read_block_addr()`.

**What changes**:
- Command becomes `$0B` instead of `$03`
- Must send 8 additional dummy clocks after the 24-bit address (total: 5 bytes command instead of 4)
- Removes the 50 MHz clock ceiling — chip now supports up to 133 MHz

**Impact at current clock rate (sysclk/8)**: Negligible — the extra dummy byte costs 0.2 µs per read, but the clock rate doesn't change without also modifying the bit-bang loop.

**Why do it**: This is a prerequisite for options 2 and 3. Without this change, faster SPI clocks would violate the `$03` command's 50 MHz limit.

**Implementation**: ~5 lines changed in `flash_read_block_addr()`.

### Option 2: Streamer-Based Bulk Transfers — Moderate Effort, 2–3x Read Speedup

**Change**: Replace the `flash_send()` and `flash_receive()` bit-bang loops with streamer-based transfers for bulk data (256+ bytes). Keep the bit-bang approach for short command sequences (1–5 bytes).

**What changes**:
- Add `XINIT`/`WAITXFI` streamer code for page-sized and block-sized transfers
- Adjust `wxpin` to set a faster clock period (e.g., `#2` for sysclk/4 = 80 MHz at 320 MHz sysclk)
- Requires Fast Read (`$0B`) — see Option 1

**Impact**: 2.0–3.2x faster reads (10–16 MB/s at 320 MHz sysclk). Negligible write improvement.

**Complexity**: Moderate — the streamer mode word configuration and clock alignment require careful timing. The P2 boot ROM's `flash_loader` is a proven reference implementation of streamer-based SPI flash access.

**Trade-off**: The current implementation works at any sysclk from DC to 350+ MHz. A streamer-based approach would need the NCO frequency set correctly for the system clock, and timing alignment verified at the target speed.

### Option 3: Dual SPI Reads — Higher Effort, 4–5x Read Speedup

**Change**: Use Dual Output Fast Read (`$3B`) or Dual I/O Fast Read (`$BB`) to read 2 bits per clock cycle.

**What changes**:
- MOSI (P59) becomes bidirectional — output during command/address, input during data
- Both P58 and P59 carry data during the read phase
- Streamer configured for 2-pin capture mode
- Pin direction switching in PASM between command and data phases

**Impact**: 4.0–5.3x faster reads (20–26 MB/s). No write improvement.

**Complexity**: High — requires bidirectional pin management, Dual SPI timing verification, and more complex streamer mode words. Must verify that the P2 Edge module's board layout supports the signal integrity needed at >80 MHz dual-data rates.

**Hardware constraint**: The P2 Edge module connects only P58–P61 to the flash chip. IO2/IO3 are not available, so **Quad SPI is not possible** on this hardware.

### Option 4: Free the COG During Reads — Streamer Bonus

Even without increasing the SPI clock, using the streamer lets the COG **do other work** during block reads instead of being trapped in the bit-bang loop. Potential uses:

- Compute CRC on the previous block while reading the next
- Service other cog tasks or respond to lock requests
- Overlap read and processing for pipelined file operations

This is an architectural benefit, not a raw throughput improvement.

## 8. Summary

### Current Performance

| Operation | Time | Throughput | Bottleneck |
|---|---|---|---|
| 4 KB block read | 820 µs | 5.0 MB/s | SPI clock rate (40 MHz) |
| 4 KB block write | 52.3 ms | 78.3 KB/s | Flash erase (45 ms) + program (6.4 ms) |
| Mount (3,968 blocks) | ~4 ms SPI | N/A | Spin2 processing |

### Could the Streamer Help?

| Operation | Streamer Benefit | Why |
|---|---|---|
| **Block reads** | **Yes — 2x to 5x** | Removes software loop bottleneck, enables higher SPI clock |
| Block writes | No — 1.6% max | Flash internal erase/program timing dominates (98.4%) |
| Mount scan | Minimal | Small transfers, Spin2 processing dominates |
| Short commands | No | Streamer overhead exceeds bit-bang for 1–5 byte transfers |

### Recommended Path

1. **Switch to Fast Read (`$0B`)** — minimal code change, prerequisite for everything else
2. **Add streamer for block reads** — 2–3x read speedup with moderate effort
3. **Consider Dual SPI** — 4–5x read speedup, higher effort, verify signal integrity
4. **Don't optimize writes** — the flash chip's internal timing is the hard limit

### Maximum Achievable Performance (Standard SPI, This Hardware)

| Metric | Current | Best Achievable | Improvement |
|---|---|---|---|
| Read throughput | 5.0 MB/s | ~16 MB/s (streamer + Fast Read) | 3.2x |
| Write throughput | 78.3 KB/s | ~79.5 KB/s | 1.6% |
| Read (Dual SPI) | 5.0 MB/s | ~26 MB/s (streamer + Dual Fast Read) | 5.3x |
