# flash\_fs SPI Performance Analysis

An analysis of the SPI implementation in `flash_fs.spin2`, the W25Q128JV flash chip capabilities, and whether the P2 streamer could improve throughput.

- **Driver**: flash\_fs v2.1.0
- **Flash chip**: Winbond W25Q128JV (128 Mbit / 16 MB)
- **Hardware**: P2 Edge Module (Rev D) - pins P58-P61
- **Author**: Stephen M. Moraco, Iron Sheep Productions, LLC

**NOTE:** *An earlier revision of this page (written for v2.0.0) drew four conclusions the driver's own code does not support. This revision corrects them:*

- *It said writes are flash-bound. That ignored the Spin2 cost of moving one byte per call, which v2.0.0 paid for every byte of every `write()`. The Spin2 cost is now a separate line in [Section 2](#write-throughput-4-kb-block).*
- *It said `mount()` reads 1 byte per block. `mount()` reads the first byte of every block, and then reads every active block in full (4,096 bytes) and checks its CRC. See [Section 2](#mount-time).*
- *It took the read rate to be 8 system clocks per bit. The receive loop costs about 89 system clocks per byte, because the smart-pin clock restarts for each byte. See [Section 2](#read-throughput-4-kb-block).*
- *Its streamer advice is valid, but secondary to the Spin2-level work: the streamer can speed up only the SPI share of a read, and [Section 6](#6-could-the-streamer-help) now says how large that share is.*

## 1. Current SPI Implementation

The SPI layer in `flash_fs.spin2` (the private methods `flash_command()`, `flash_send()` and `flash_receive()`) uses a **hybrid smart-pin + bit-bang** approach implemented in inline PASM2.

### Pin Assignments (Fixed in Hardware)

```text
SF_CS    = 61   ' Chip select (active low)
SF_SCLK  = 60   ' SPI clock
SF_MOSI  = 59   ' Master out / slave in (DI / IO0)
SF_MISO  = 58   ' Master in / slave out (DO / IO1)
```

### Clock Generation

The SPI clock is generated by a **smart pin** in transition output mode (inverted for SPI Mode 3):

```text
wrpin  ##%001000000_01_00101_0, #SF_SCLK   ' transition output, inverted
wxpin  #4, #SF_SCLK                         ' 4 sysclk per transition
```

This gives **8 system clocks per SPI bit** (4 clocks per half-cycle x 2 half-cycles) while a byte is being clocked.

### Data Transfer

**MOSI (send)**: The COG bit-bangs data out MSB-first using `shl`/`drvc` in a tight `rep` loop (8 sysclk per bit). Hub data is streamed in via `rdfast`/`rfbyte` (the P2 hub FIFO, not the streamer).

**MISO (receive)**: The COG samples data with `testp`/`rcl` in a `rep` loop (8 sysclk per bit), writing bytes to hub via `wrfast`/`wfbyte`.

Each byte requires the COG to **reset and restart the smart pin clock** (`fltl`/`drvl`/`wypin #16`), generating exactly 16 transitions (8 SPI clocks) per byte. A `rep @.r, #1` block around this protects the clock start sequence from interrupts. The restart is part of the per-byte cost counted in [Section 2](#read-throughput-4-kb-block).

### Flash Commands Used

| Operation | Command | Opcode | Notes |
|---|---|---|---|
| Read data | Read Data | `$03` | Standard SPI, max 50 MHz clock |
| Page program | Page Program | `$02` | Standard SPI, 256 bytes/page |
| Write enable | Write Enable | `$06` | Required before every program/erase |
| Sector erase | Sector Erase (4KB) | `$20` | 45 ms typical, 400 ms maximum (datasheet) |
| Read status | Read Status Register-1 | `$05` | Polled for BUSY bit |
| Read UID | Read Unique ID | `$4B` | 64-bit unique chip ID |

## 2. Current Throughput

### SPI Clock Rate

| System Clock | SPI Clock | Calculation |
|---|---|---|
| 200 MHz | 25.0 MHz | 200 / 8 |
| 300 MHz | 37.5 MHz | 300 / 8 |
| 320 MHz | 40.0 MHz | 320 / 8 (common in test/demo code) |
| 350 MHz | 43.75 MHz | 350 / 8 |

All of these are under the 50 MHz limit of the Read Data (`$03`) command, so the implementation works correctly. This is the rate **within** a byte. Between bytes the loop adds the restart cost below, so the rate a block read achieves is lower.

### Read Throughput (4 KB Block)

The receive loop in `flash_receive()` costs, per byte, by the instruction timings in its source comments:

```text
rep @.r,#1 (2) + fltl (2) + drvl (2) + wypin (2) + waitx #7 (2+7)  =  17 clocks
8 bits x (waitx #2 (2+2) + testp (2) + rcl (2))                     =  64 clocks
rep setup (2) + wfbyte (2) + djnz (4)                               =   8 clocks
                                                                      --------
Per byte                                                               89 clocks
```

That is a count from the source, not a measurement. It gives:

```text
4096 bytes x 89 clocks = 364,544 system clocks per 4 KB block
At 320 MHz:  364,544 / 320 MHz = 1,139 µs per block  (3.6 MB/s)
```

The earlier revision of this page took 8 clocks per byte-bit and no restart, which gives 820 µs per block (5.0 MB/s at 320 MHz). The restart and loop overhead add 25 clocks per byte (89 against 64 for the eight bits), so a block read takes about 1.4 times as long as the clocking alone.

The share of a driver-level block read that this SPI work takes is a bench measurement:

**[measured at bench visit 7: SPI_SHARE]** - the SPI share of block-read time after the Spin2-level speed-up, as a percentage of `read()` time for a 690 KB file, with clkfreq stated.

### Write Throughput (4 KB Block)

Writing a 4 KB block involves one sector erase and 16 page programs. The flash chip's own time, at the datasheet's typical values, is the floor:

```text
Sector erase (tSE typical):                            45,000 µs
16 pages x Page Program (tPP typical 400 µs):           6,400 µs
                                                       --------
Flash time per block:                                  51,400 µs  (51.4 ms)

Ceiling:  4096 B / 51.4 ms  =  79.7 KB/s
```

On top of that, each block pays for the SPI transfers (command bytes, 16 pages of 256 bytes, status polls) and for the Spin2 that moves the caller's bytes into the block buffer. v2.0.0 moved them one byte per call: the reporting user measured about 12 µs per `rd_byte_no_locks` call, and at 4,088 bytes per block the write loop costs about 49 ms of Spin2 per block, serialized with the 51.4 ms of flash time. So v2.0.0 wrote at about half the flash-bound ceiling. v2.1.0 copies runs of bytes with `bytemove` instead.

**[measured at bench visit 7: SPEEDUP_TABLE]** - the write rows (4 KB, 64 KB and 690 KB), before and after, in clock ticks and µs with clkfreq stated.

The flash erase and program times are the datasheet's typical values, and they stay the floor: no SPI or Spin2 change takes a block write below 51.4 ms.

### Mount Time

`mount()` reads the first byte of every one of the 3,968 blocks. Every block whose first byte shows an active lifecycle is then read in full (4,096 bytes) and its CRC is checked. A mount of a flash holding N active blocks therefore spends about N times the block-read time above on SPI alone (1,139 µs per block at 320 MHz, counted), plus the 3,968 first-byte reads and the Spin2 that builds the tables. `mount()` is not a 4 ms operation; it grows with the amount of data on the flash.

`can_mount()` makes the same reads.

**[measured at bench visit 7: SPEEDUP_TABLE]** - the `mount()` and `can_mount()` rows, with the number of files and blocks present stated.

## 3. Flash Chip Capabilities

The W25Q128JV supports three SPI interface modes:

### Read Performance

| Command | Opcode | Mode | Max Clock | Bits/Clk | Peak Throughput |
|---|---|---|---|---|---|
| Read Data | `$03` | Standard (1-1-1) | **50 MHz** | 1 | 6.25 MB/s |
| Fast Read | `$0B` | Standard (1-1-1) | 133 MHz | 1 | 16.6 MB/s |
| Fast Read Dual Output | `$3B` | Dual out (1-1-2) | 133 MHz | 2 | 33.3 MB/s |
| Fast Read Dual I/O | `$BB` | Dual I/O (1-2-2) | 133 MHz | 2 | 33.3 MB/s |
| Fast Read Quad Output | `$6B` | Quad out (1-1-4) | 133 MHz | 4 | 66.5 MB/s |
| Fast Read Quad I/O | `$EB` | Quad I/O (1-4-4) | 133 MHz | 4 | 66.5 MB/s |

The driver uses **Read Data (`$03`)**, which limits the clock to **50 MHz**. Switching to **Fast Read (`$0B`)** would unlock clock rates up to **133 MHz** - the only cost is 8 extra dummy clocks per transaction.

### Write Performance

| Command | Opcode | Mode | Page Size | Internal Time (typ) |
|---|---|---|---|---|
| Page Program | `$02` | Standard (1-1-1) | 256 B | 0.4 ms |
| Quad Page Program | `$32` | Quad input (1-1-4) | 256 B | 0.4 ms |

The chip's internal program and erase time is a floor that no SPI change moves:

- At 133 MHz standard SPI: 256 bytes transfer in 15.4 µs, but the internal program takes 400 µs
- Even with an instantaneous SPI transfer, the flash time alone limits a block write to the 79.7 KB/s ceiling in [Section 2](#write-throughput-4-kb-block)

The driver's measured write rate sits below that ceiling by the Spin2 and SPI time that [Section 2](#write-throughput-4-kb-block) lists. The Spin2 part is where v2.1.0 gained; the SPI part is what a streamer could shrink.

### Erase Timing

| Command | Size | Typical | Maximum |
|---|---|---|---|
| Sector Erase (`$20`) | 4 KB | 45 ms | 400 ms |
| Block Erase (`$52`) | 32 KB | 120 ms | 1,600 ms |
| Block Erase (`$D8`) | 64 KB | 150 ms | 2,000 ms |
| Chip Erase (`$C7`) | 16 MB | 40 s | 200 s |

## 4. P2 Edge Hardware Constraints

The P2 Edge Module connects **only 4 pins** to the SPI flash chip:

| Pin | Flash Signal | SPI Role |
|---|---|---|
| P58 | DO (IO1) | MISO - data out from flash |
| P59 | DI (IO0) | MOSI - data in to flash |
| P60 | CLK | SPI clock |
| P61 | /CS | Chip select |

**IO2 (/WP) and IO3 (/HOLD)** on the W25Q128JV are **not connected** to P2 GPIO pins. They are typically tied high on the module.

### Consequence

- **Quad SPI is not possible** - requires IO2 and IO3
- **Dual SPI is possible** - uses IO0 (P59) and IO1 (P58) bidirectionally. Both pins are available and adjacent to the clock, with smart pin routing reachable (P59 = SF\_SCLK - 1, P58 = SF\_SCLK - 2)
- **Standard SPI** is the current and simplest mode

## 5. P2 Streamer Overview

The P2 streamer is a hardware DMA engine built into each COG. Once started, it moves data between hub memory and pins **at the system clock rate** with **zero COG involvement** - the COG can do other work or wait with `WAITXFI`.

### How It Works

1. **Set up the hub FIFO**: `RDFAST` (hub to streamer to pins) or `WRFAST` (pins to streamer to hub)
2. **Set the data rate**: `SETXFRQ` programs an NCO to control bit timing
3. **Start the transfer**: `XINIT mode, count` begins streaming
4. **Wait for completion**: `WAITXFI` blocks until all data is transferred

The mode word encodes: direction, pin number, bit width (1/2/4/8/16/32), byte order, and transfer count.

### Key Modes for SPI

| Mode Constant | Value | Purpose |
|---|---|---|
| `X_RFBYTE_1P_1DAC1` | `$8000_0000` | Stream bytes from hub FIFO to 1 pin (SPI MOSI) |
| `X_1P_1DAC1_WFBYTE` | `$C000_0000` | Capture 1 pin to bytes in the hub FIFO (SPI MISO) |
| `X_PINS_ON` | `$0080_0000` | Enable pin output |
| `X_ALT_ON` | `$0001_0000` | MSB-first bit order |

### Streamer vs. Current Bit-Bang

| Aspect | Current (Bit-Bang) | Streamer |
|---|---|---|
| COG busy during transfer? | Yes - `rep` loop for every bit | No - set-and-forget |
| Max data rate | sysclk/8 within a byte, 89 clocks per byte overall | sysclk/2 (hardware) |
| Hub memory access | `rfbyte`/`wfbyte` (manual) | Automatic via FIFO |
| Setup complexity | Simple inline PASM | Mode word configuration |
| Per-byte overhead | Clock restart sequence | None (continuous) |

The critical difference: the current implementation is limited by the software loop, which restarts the clock for every byte. The streamer can output and capture bits at up to **2 sysclk per bit**.

## 6. Could the Streamer Help?

### Reads: Yes, for the SPI share of the time

The streamer would help reads in two ways:

1. **Higher SPI clock rate**: Remove the per-byte restart and the 8-sysclk-per-bit software loop. With the streamer, the SPI clock can go as fast as the flash chip allows.

2. **Free the COG**: During a 4 KB block read, the COG currently spends about 364,544 clocks in the `rep` loops. With the streamer, the COG issues `XINIT` + `WAITXFI` and is free to do other work (for example CRC computation on previously read data).

**However**, there are two limits:

- A prerequisite is switching from **Read Data (`$03`)** to **Fast Read (`$0B`)**. The `$03` command limits the clock to 50 MHz - even with the streamer, you would only gain from 40 MHz to 50 MHz. Fast Read unlocks the full 133 MHz chip limit.
- A streamer shortens only the SPI time. What it can gain from a driver-level read is bounded by the SPI share of that read: if SPI is a fraction *s* of the time `read()` takes, the best case is a speed-up of 1 / (1 - *s*), however fast the SPI becomes. The share, after the Spin2 speed-up, is the measurement in [Section 2](#read-throughput-4-kb-block): **[measured at bench visit 7: SPI_SHARE]**.

Streamer work was ranked behind the Spin2-level work for this reason: v2.0.0 spent most of a read in Spin2, one call per byte, and moving bytes in runs removed that cost first.

#### Projected SPI Time for a 4 KB Block

These rows are arithmetic on the clock rate, not measurements. They show the SPI time only, at 320 MHz:

| Configuration | SPI Clock | 4 KB SPI Time | vs. Current SPI Time |
|---|---|---|---|
| **Current** (bit-bang, `$03`, 89 clocks per byte) | 40 MHz within a byte | 1,139 µs | baseline |
| Streamer, `$0B`, sysclk/4 | 80 MHz | 410 µs | 2.8x |
| Streamer, `$0B`, sysclk/3 | 106 MHz | 309 µs | 3.7x |
| Streamer, `$0B`, sysclk/2.5 | 128 MHz | 256 µs | 4.5x |

At 320 MHz sysclk, sysclk/2 = 160 MHz, which exceeds the chip's 133 MHz maximum. The practical ceiling is around **128 MHz** (sysclk/2.5).

#### Dual SPI (If Implemented)

| Configuration | SPI Clock | 4 KB SPI Time | vs. Current SPI Time |
|---|---|---|---|
| Streamer, Dual `$3B`, 80 MHz | 80 MHz | 205 µs | 5.6x |
| Streamer, Dual `$BB`, 106 MHz | 106 MHz | 155 µs | 7.4x |

Dual SPI doubles the data rate per clock by using both IO0 and IO1 for data. The streamer supports 2-pin modes natively.

### Writes: the flash dominates, and the Spin2 and SPI cost is the rest

For a block write the chip's own 51.4 ms of typical erase and program time (see [Section 2](#write-throughput-4-kb-block)) is the floor. The SPI transfers are about 16 pages of 256 bytes plus commands: a small share of that floor. A streamer cannot take a block write below the floor, and the share it can remove is the SPI part of the gap between the measured write time and the floor.

**[measured at bench visit 7: SPEEDUP_TABLE]** - the write rows give that gap.

### Mount: the SPI reads are large

`mount()` reads every active block in full (see [Section 2](#mount-time)), so on a flash holding many files the SPI time is the larger part of a mount, not a negligible one. A streamer-based receive would shorten it in proportion to the SPI share. The first-byte reads of the free blocks are short transfers, where the streamer's setup cost exceeds the bit-bang cost.

## 7. Improvement Options

Ranked by impact and implementation effort. Each applies to the SPI share only; the Spin2-level run copy already shipped in v2.1.0.

### Option 1: Switch to Fast Read (`$0B`) - Easy, Unlocks Future Gains

**Change**: Replace the Read Data command (`$03`) with Fast Read (`$0B`) in `flash_read_block_addr()`.

**What changes**:
- Command becomes `$0B` instead of `$03`
- Must send 8 additional dummy clocks after the 24-bit address (total: 5 bytes command instead of 4)
- Removes the 50 MHz clock ceiling - the chip now supports up to 133 MHz

**Impact at the current clock rate (sysclk/8)**: Negligible - the extra dummy byte costs the time of one more byte per read, and the clock rate does not change without also modifying the bit-bang loop.

**Why do it**: This is a prerequisite for options 2 and 3. Without this change, faster SPI clocks would violate the `$03` command's 50 MHz limit.

**Implementation**: About 5 lines changed in `flash_read_block_addr()`.

### Option 2: Streamer-Based Bulk Transfers - Moderate Effort

**Change**: Replace the `flash_send()` and `flash_receive()` bit-bang loops with streamer-based transfers for bulk data (256+ bytes). Keep the bit-bang approach for short command sequences (1-5 bytes).

**What changes**:
- Add `XINIT`/`WAITXFI` streamer code for page-sized and block-sized transfers
- Adjust `wxpin` to set a faster clock period (for example `#2` for sysclk/4 = 80 MHz at 320 MHz sysclk)
- Requires Fast Read (`$0B`) - see Option 1

**Impact**: The SPI time of a block read falls 2.8x to 4.5x (the table in [Section 6](#6-could-the-streamer-help)); the whole-read gain is capped by the SPI share. Negligible write improvement.

**Complexity**: Moderate - the streamer mode word configuration and clock alignment require careful timing. The P2 boot ROM's `flash_loader` is a proven reference implementation of streamer-based SPI flash access.

**Trade-off**: The current implementation works at any sysclk from DC to about 350 MHz (the driver header says its SPI timing is not verified above that). A streamer-based approach would need the NCO frequency set correctly for the system clock, and timing alignment verified at the target speed.

### Option 3: Dual SPI Reads - Higher Effort

**Change**: Use Dual Output Fast Read (`$3B`) or Dual I/O Fast Read (`$BB`) to read 2 bits per clock cycle.

**What changes**:
- MOSI (P59) becomes bidirectional - output during command/address, input during data
- Both P58 and P59 carry data during the read phase
- Streamer configured for 2-pin capture mode
- Pin direction switching in PASM between command and data phases

**Impact**: The SPI time of a block read falls 5.6x to 7.4x. No write improvement.

**Complexity**: High - requires bidirectional pin management, Dual SPI timing verification, and more complex streamer mode words. The P2 Edge module's board layout would need to support the signal integrity needed at more than 80 MHz dual-data rates.

**Hardware constraint**: The P2 Edge module connects only P58-P61 to the flash chip. IO2/IO3 are not available, so **Quad SPI is not possible** on this hardware.

### Option 4: Free the COG During Reads - Streamer Bonus

Even without increasing the SPI clock, using the streamer lets the COG **do other work** during block reads instead of being held in the bit-bang loop. Potential uses:

- Compute CRC on the previous block while reading the next
- Service other cog tasks or respond to lock requests
- Overlap read and processing for pipelined file operations

This is an architectural benefit, not a raw throughput improvement.

## 8. Summary

### Current Performance

| Operation | Figure | Limit |
|---|---|---|
| 4 KB block read (SPI only) | 364,544 clocks, 1,139 µs at 320 MHz (counted from the source) | SPI loop: 89 clocks per byte |
| 4 KB block write (flash only) | 51.4 ms at the datasheet's typical times | Flash erase (45 ms) + 16 page programs (6.4 ms) |
| `mount()` | N active blocks x the block-read time, plus 3,968 first-byte reads | Active blocks read whole and CRC'd |
| Driver-level read, write and mount rates | **[measured at bench visit 7: SPEEDUP_TABLE]** | Spin2, SPI and flash together |

### Could the Streamer Help?

| Operation | Streamer Benefit | Why |
|---|---|---|
| **Block reads** | Up to the SPI share of the read | Removes the per-byte clock restart and the software loop; capped by 1 / (1 - SPI share) |
| Block writes | Small | The flash's 51.4 ms floor dominates, and the SPI transfers are a small part of the rest |
| Mount | In proportion to the SPI share | Every active block is read in full |
| Short commands | No | Streamer setup exceeds the bit-bang cost for 1-5 byte transfers |

### Recommended Path

1. **Spin2-level run copies first** (done in v2.1.0): the per-byte call cost was the larger part of a read and of a write.
2. **Measure the SPI share** after that ([Section 2](#read-throughput-4-kb-block)), and decide on a streamer from the figure.
3. **Switch to Fast Read (`$0B`)** - minimal code change, prerequisite for everything else that raises the clock.
4. **Add the streamer for block reads** - moderate effort, gain bounded by the SPI share.
5. **Consider Dual SPI** - higher effort, verify signal integrity.
6. **Do not expect writes to pass the flash floor** - the chip's internal timing is the hard limit.
